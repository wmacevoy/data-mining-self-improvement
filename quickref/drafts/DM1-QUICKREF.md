# DM1 quick reference

One line per principle of DM1, a guide of 100 data-mining guidelines for humans and agents, condensed so a reader who will never open the chapters gets the move and its reason. It is read beside SE1's quick reference and assumes it: each DM1 principle either reframes an SE1 principle for data or is new, and a line here says what data work adds. These are guidelines, not law: they point, and you decide; where a line leaves a hole, that hole is a place to decide in. The ID finds the full text in `guide/` when a line is not enough.

## 1. Purpose

- **DM1/P1** Software asks whether the thing works; data asks whether the claim is true and whether anyone would act differently if it were. The fifth constraint, usually the honest one to move, is the question: narrowing it, one lot instead of all, is the commonest form of success. Resources are rows, labels, compute, and the hours of whoever knows what the columns mean.
- **DM1/P2** Accurate is a property of a model against a held-out sample; true is a property of a claim that must survive selection bias, drifting definitions, proxy labels, and people who change once watched. A claim worth acting on carries its interval, its population, and the conditions under which it stops holding.
- **DM1/P3** The people whose rows you model did not agree to the question, never see the output, and meet only its consequences; `groupby("lot")` and `groupby("plate")` look the same, and the second is about people. What reduces their discomfort: minimization, aggregation, recourse. Nobody wanting to re-run the pipeline is information about the pipeline.
- **DM1/P4** Recorded seeds, one command back to raw, a dumb baseline, a holdout touched once, grouped and time-ordered splits, row-count assertions, a plan written first: each retires a named fear. A leaking split or 99% on a 99%-negative class looks the same and retires nothing. A wrong bridge falls down; a wrong number just gets used.
- **DM1/P5** The deliverable is the claim plus someone else's ability to reproduce, challenge, and update it next quarter. A notebook records cells, not the order they ran, and the order is the program: keep notebooks for looking and the method in code a command runs from raw. For a claim in prose, the means is a check rather than a re-derivation.

## 2. Unknowing

- **DM1/U1** Mining is discovering which K each column and step is. K1 to K0: profile, plot, ask who collected it. K2 to K1: run end to end on real data early, show an expert, score on a period you did not develop on. K3 to K0: a check that could have failed, a baseline that could have won, a second person. K2 here is a certainty, arriving as "that column means something different before 2024"; plan for the sentence.
- **DM1/U2** Wrong software stops; wrong analysis continues and produces a chart: a join that duplicates rows returns a frame, a `dropna()` that removes the interesting cases returns a cleaner table, a half-written partition reads as current. Give each a way to say wrong: counts asserted across every join, keys unique, ranges at the boundary, every stage overwriting its own partition, and what you find on resuming torn until a run from raw agrees.
- **DM1/U3** Leakage is any path by which the answer reaches training that will not exist at prediction: a feature encoding the label, the same lot and night on both sides of a split, an "arrival" column that is really upload time. It feels like a good result, because everything you would use to catch an error is the thing being fooled, so it is found by reading when each value became knowable, never by the score. A result too good for the problem is a bug report until one prediction is traced to rows that existed at the prediction point.
- **DM1/U4** Every model is a chosen falsehood: rows independent, sample representative, past is future, label is truth, missing at random, a day is 24 hours, de-identified is anonymous. Name each and what breaks when it fails: independence, and intervals are too narrow; stationarity, and the backtest was fiction. Between a chosen K4 and K3 is one written sentence.
- **DM1/U5** "Two days to clean this" is a K0 statement about K2 work. Time-box cleaning and exploration, each box ending on a fence; estimate modeling from a known-good feature table with a fixed metric and split. "I'll know by Thursday whether the gate data is usable" is honest; "the model will be done Thursday" hides a cleaning box inside a modeling estimate.
- **DM1/U6** A classifier shown something unlike its training data does not raise; it returns a class, often confidently, and an interrupted retrain's checkpoint answers as confidently as the finished model. Cheapest first: check inputs against the training envelope and refuse or flag outside it; calibrate, checked on data not fit on; abstain below a confidence and count how often, since a rising abstention rate is a drift alarm needing no labels.
- **DM1/U7** A mean, a correlation, or an accuracy is a summary that dropped things without knowing what; Anscombe's four datasets share them all and look nothing alike. Check from outside with a plot and raw rows, at random and then the extremes that most disagree; for a document, the text layer is a summary of the page, so look at the page. As a habit this is the step the deadline skips, so have the command that makes the number also print the plot and the ten rows that most disagree.
- **DM1/U8** "Will I get the loan" asks about one case; the data answers with a rate among rows the model cannot tell from it, a class fixed by which columns were recorded. A probability for one case is a property of that reference class: say so and name the class; putting yourself in the data does not fix it. Sparse groups are pooled toward the majority, so for a minority the gap can be systematic in one direction, which is bias, found only by looking.
- **DM1/U9** Time with no agenda is where K2 lives, and data work can afford it less, because every look at the outcome that changes what you try next spends evidence. Whitespace on the inputs (raw rows, extremes, the datasheet, a column over time) is free and selects for nothing; on the outcome, a subgroup noticed or a residual plot pored over, it is a look and goes in the ledger. Point the time at the inputs and write what it finds in FINDINGS or the datasheet, not into a feature.
- **DM1/U10** An absence is the cheapest K3: it takes no evidence to report and looks like diligence, and a search that could not have found the thing returns the same answer as one that found nothing. Every "none" says how it was looked for and what was not searched; see the search find a planted case first; before reporting something missing across many cases, open one by hand.
- **DM1/U11** An AUC of 0.91 is K0; that the model is good enough to change what the supervisor does on Saturday is a judgment, and "the model passes" stops the question being asked. Calibration, latency, and error on a named slice convert into requirements with a bar; the rest is marked *(judged)*, with the judge reading the output in the decision's terms, and a bias measure is a proxy too. A verdict belongs to a version: a new extract, retrain, or moved threshold makes it stale unless a retrain policy the judge approved covers it. An agent records a verdict and never gives one.

## 3. Feedback

- **DM1/F1** Tests of the code are free: re-run a transform, swap a model class. Tests of the claim are not: a training run, a labeling campaign, an expert's hour. Some are one-way: a look at the holdout, a published number someone acts on, a survey fielded once. The one-way decisions mostly come in the first week, while they still feel cheap: the question, the unit, the outcome, the split, the labeling scheme.
- **DM1/F2** The toolkit: pure functions over frames, a tiny fixture with hand-worked answers, seeds fixed and recorded with the result, one command from raw to every reported number, assertions on what joins and filters break, caches that record when and from where. Lowering the cost of checking a result multiplies against every future question; a result that is hard to check is information about the analysis.
- **DM1/F3** Loops by cost: look at the data, pipeline assertions, a unit test on a transform, the fixture end to end, the baseline comparison, the holdout (spendable), human review of the claim (the metric does not measure the decision), a domain expert on the output, prospective use. No suite detects "we measured the wrong thing"; only a person who knows the domain does.
- **DM1/F4** In software a search leaves no residue; in data it contaminates: try forty features or subgroups and keep the best, and what you kept was selected for looking good, some of it noise. A result is real to the degree it would have survived being the only thing tried. Association rules, clustering with a chosen *k*, anomaly thresholds are searches over thousands of candidates: correct for the count and confirm survivors on data the search never saw. A hyperparameter search is an adversary you hired; given freedom it finds your leakage and hands it back as a win.
- **DM1/F5** You cannot un-see the test set: each look reacted to moves some of its information into the model by way of your judgment, leaving no trace in git, and twenty such looks make a validation set wearing a test set's name. Split it off first, before exploring, where casual code cannot reach it; develop on validation or cross-validation; spend the holdout at a decision; when it is spent, say so and get a fresh one, a later period or a new site.
- **DM1/F6** "We tried one model" and "we tried sixty" are different claims about the same score, and the second is almost never reported. Record the count mechanically: a ledger line appended by the code each time anything is scored (in retrieval, each search run and page read), and an analysis plan written before the outcome is examined, so a departure is visible. Report it: "best of 23 on validation; one look at the holdout."
- **DM1/F7** A number without an interval is equally uncertain and less honest; 0.84 against 0.82 is not better inside the noise of a 1,200-row test set. Three spreads, routinely ignored: the sample (a bootstrap or analytic interval), the seed (train five times; a gain smaller than the seed spread is not a gain), the split (time-ordered data gets time-ordered splits, and rows sharing a lot, a night, or an event stay on one side).
- **DM1/F8** As a sample grows, variance shrinks and bias does not: a large biased sample converges confidently on the wrong number, so "we have millions of rows" does not answer "who is missing?" Sensors drop off the network most when the lot is busiest; five years of readings describe the quiet hours very precisely.
- **DM1/F9** Here the optimizer gaming the measure is usually not a person but the training loop, the search, or an agent re-running until the score rises, none knowing what the metric was a proxy for: aim at accuracy on an imbalanced class and get the majority; at a rubric, the rubric. Report more than one metric, including one the search was not told about, and look at individual predictions. A limit is a target too: cap a summary's length and summaries crowd under the cap; telling the writer it gives way to evidence is a rule read and not followed, and comparing drafts by script is what changes the work.
- **DM1/F10** A citation check holds what a summary says to its source and cannot see what it stopped saying: fidelity is precision and measures no recall, a length limit is a filter on the data chosen by nobody, and the author is a poor witness to its own cuts. Keep the drafts and compare draft with final by script; have a second reader, blind to the first, read a sample of cases whole and count what each missed; name in advance what may never be cut; when limit and evidence conflict, the limit gives way.

## 4. Requirements

- **DM1/R1** The solution arrives as a technique, "machine learning to find patterns"; the pain is a decision someone makes badly today: who makes it, when, with what in front of them, what it costs when wrong. Then: what would you do differently if the answer came out the other way? "Nothing" means the analysis is a hobby, and should be budgeted as one.
- **DM1/R2** Three definitions decide everything downstream and each costs a re-analysis to change: the unit of analysis (one row is one what; it decides independence, how the split is grouped, and what *n* means), the outcome (not "full" but a sentence you could write as a query), the prediction point (every feature must be knowable at that moment, and everything after it is leakage). A claim with no outcome to wait for fixes what stands in for them.
- **DM1/R3** "A good model" cannot be rejected; "within fifteen minutes for 80% of events, against a baseline managing 55%, on the season we have not looked at" can, and being rejected in week one is the point. Write the bar before seeing results, or it is set to the score. A retrieval system's bar is how much of what a full reading finds it must find. A bar can say no; it cannot say worth acting on, so write who judges that, on what, and when.
- **DM1/R4** A classifier's requirement has at least two prices, rarely equal: predicted full and wasn't (drivers sent far, empty spaces) against predicted space and was full (a queue at the gate). Get the ratio from the client, even roughly, and choose the threshold from it: a business decision, not a hyperparameter. Accuracy prices both the same and is almost never the metric the client needs.
- **DM1/R5** Whatever pandas does with a missing value becomes the method, chosen by nobody. Absent: why before how to fill; a sensor unreachable at peak is the peak, and `dropna()` deletes the event. Late: revised next month, and a cache pins today's version forever. Wrong: units changed, `-999`, a timezone not what the column says; a range check and a plot find most. Lying: a zero meaning "no reading" among zeros meaning "empty," an imputed value indistinguishable from a measured one; it passes every schema check, and only provenance finds it. The adversary is your own search, your model changing what it measures, or people learning what the score rewards.
- **DM1/R6** Train on data as it looks now, score on the past, and you have used the future: final attendance, a corrected reading, a label applied later sit in the row with nothing saying they arrived later. Per column, write in the datasheet when the value became available to someone who could act on it, and build features with as-of joins that respect it.
- **DM1/R7** A label was applied by someone, under instructions, at a time, for a purpose that may not be yours. Measure how often two labelers disagree on a sample: the model is bounded by that rate. Ask what it is a proxy for: a label recording past treatment teaches the model to repeat it. A labeling scheme is a requirement; version it like one.
- **DM1/R8** The finite, usually unwritten resources: events, not rows, since five seasons of readings may be eighty events and the rare unit limits you; labels, at what cost and by when; compute per run and how many runs the plan assumes; expert hours, often the scarcest; inference cost per call, and tokens per document when a model reads the corpus; freshness, how stale the model may get and who decides.
- **DM1/R9** When rows are people: who is missing and what does the model do to them; is the label a proxy for what you care about or for how people were treated; can the scored person contest the score. The safest record is never kept; the second safest is the aggregate instead of the row. Law adds that the purpose collected for is often the only purpose allowed, plus retention and the provenance of training data. Security adds that a model can leak its training data, inputs can be poisoned, and ZIP, birth date, and sex identify most people. Adding plate reads is one join in code and a new kind of system in the requirements.
- **DM1/R10** Bias is a systematic gap between what the data estimates and what is true for the cases it is used on: a property of the pipeline, measured or present unmeasured, entering as historical, selection, measurement, aggregation, evaluation, deployment, and unequal treatment. The requirements say which groups matter, which gap is unacceptable, measured how (error rate, calibration, or selection rate per group), and who decided; the measures conflict when base rates differ, and choosing is the client's, with the affected people represented. Groups need not be demographic, and bias is not only about people: a forecast late for the small lots is biased against them.
- **DM1/R11** A model's non-goals are populations, conditions, and uses: lots that did not exist in training, events larger than any seen, staffing when it was built for signage. Each is a place it will still return an answer. Written, they are the model card's out-of-scope section and the envelope checks at its input; unwritten, whoever uses it for them discovers them.
- **DM1/R12** Say first whether the claim is predicted (scored against an outcome arriving later), described (a held-out period or sample), explained (an experiment or a stated causal design), or extracted (the document itself, which a person can check at the page), since that decides what it is scored against and what stands in for the prediction point. An extracted claim can be checked per quotation, and the check cannot see what was left out. Where a principle does not bind your kind, say so and why rather than fill its template with something invented.

## 5. Design

- **DM1/D1** The code is small and the state is everything else: raw pulls, clean tables, feature tables, splits, weights, vector indexes, cached responses, and all of it persists, is shared ("the clean table" means two versions), ages, and changes while observed. A trained model is state, not code: it cannot be read, only re-derived or tested, and a change reaches every prediction at once.
- **DM1/D2** A trained model is a cache of the input-outcome relationship as of its training window; drift is staleness with a statistical name. An API pull without a fetch time and refresh rule is a time machine; a vector index is a cache of the corpus under one embedding model, so store the model's name with it; a feature table is a cache of the code that built it. Put the age in the data: `fetched_at`, `trained_through`.
- **DM1/D3** Each training row has its own "now," its prediction point, and a join on today's tables gives every historical row every later correction: leakage by construction. An as-of join takes, per row, the latest value whose available-at time precedes the prediction point. That needs two times per value, when it was true and when it became known; most sources store only the first, so write down the lag you assume.
- **DM1/D4** A pipeline gets re-run after a crash, a fix, or a doubt; a stage that appends doubles its output, and a count of events just looks busier. Overwrite your own partition (this day, this lot, this run). Incremental fetches start from the last recorded high-water mark, de-duplicate on a key, and make a full re-fetch a flag, not a deletion.
- **DM1/D5** Timestamps are data: UTC with explicit offsets inside, local at the edges, once. Then decide what a day is, because a daily aggregate over UTC splits an evening event across two days and disagrees with the local chart beside it. Two local days a year are 23 and 25 hours, and a naive series shows a phantom gap in spring and a negative step in fall; test both boundaries.
- **DM1/D6** Raw stays exactly as it arrived, with where and when; everything downstream, to the number in the slide, is derived by code and rebuilt by one command. A model is a function of data version, code version, seed, and environment: record all four, or the model is an orphan whose misbehavior cannot be traced. Where raw is not yours and can change, hash each file on arrival: detection, which is what you can have.
- **DM1/D7** Each transform is a function from frames to a frame: no fetching, paths, globals, clock, or unseeded randomness inside; fetching, caching, and plotting at the edges. A notebook is for calling those and looking at what returns, not for defining them: hidden state and out-of-order cells make its real program unknowable. A cell worth keeping moves into a module with a test.
- **DM1/D8** For a model, accidental complexity is measured against the baseline: 400 features beating "same as last comparable event" by two minutes inside the seed spread bought nothing and must still be carried, monitored, explained, retrained. Prefer the simplest model whose margin survives the interval; every feature is a dependency on a source that can go absent, late, wrong, or lying.
- **DM1/D9** One definition per named quantity, and the expensive violation is train/serve skew: a feature computed one way in training and another where served, which no offline metric can see. One function imported by both; the same for metrics, the outcome, and "day." Here the mission is the decision the work serves, and the fundamental shape holds guidelines like raw is read-only, one definition per feature, every score in the ledger; both at the top of the question.
- **DM1/D10** A model cannot be read inside, so its contract carries more: inputs and units, the population and period trained on, metrics by slice with intervals, behavior outside its envelope, uses it is not for. That is the model card; a dataset's equivalent is the datasheet.
- **DM1/D11** A number tracked for a year is an interface with dependents: comparisons, targets, decisions. Change it, never silently: name the new one, run both for a while, say when the old one stops. A published number has an installed base of at least one decision.
- **DM1/D12** A deployed model costs weekly: monitoring, retraining, its data dependencies, its feature pipeline, the person who answers for it; the model code is the small box. It is perishable with no expiry printed: someone owns whether last year's model is still true, with a date to ask it, and asks what can be deleted.
- **DM1/D13** A number with no lineage is a rumor, at four layers: a value is measured, imputed, or defaulted (keep a flag; for a document, read by text layer, recognition, or eye); a dataset was collected by whom, of whom, under what consent, with what excluded before it reached you; a label by whom, under which instructions, at what agreement; a result from which data version, commit, seed, and environment, the layer people skip.

## 6. Testing

- **DM1/T1** The test that would pass when it works is the evaluation harness, split, metric, bar, and report, built before any model, with the dumbest contestant entered first: the mean, the majority class, "same as last time." Its bugs surface while stakes are low, "beats the baseline by more than the interval" is the done sentence, and sometimes the baseline wins, cheaply. For retrieval, the baseline is a full reading.
- **DM1/T2** Assertions that run every time on real data: row counts across every join and filter (equal, at most, within a range), key uniqueness, a monotone gap-checked time index, units and plausible ranges where data enters, fractions missing and defaulted against the last run. Each turns a returned value back into an exception; a failed assertion that stops a run is a gift.
- **DM1/T3** Data tests tend to assert shape, non-empty, column exists, which passes on garbage, and a fixture too small never reaches the logic: one day into a daily aggregate is one row, and a rolling z-score over it is `NaN`. Make fixtures large enough for every branch and assert hand-worked values. Every instrument that judges a result, a metric script, a labeler, an LLM judge, a search reporting an absence, must be seen to disagree with a bad answer first.
- **DM1/T4** The untrusted loop here is a metric that moves with nothing changed: unseeded randomness, nondeterministic order, a source returning a different revision, a cache that may be stale. After the third unexplained wobble a real regression gets the same shrug. Make every run reproduce its number or report its expected spread, so a move outside it means something.
- **DM1/T5** A seed is necessary and not sufficient: GPU kernels, threads, library versions, and summation order move results across machines. Decide per claim: identical (transforms on a fixed input, splits; test with equality), within a tolerance (model outputs, metrics, exports; the tolerance from observed spread, not from what passes), within a distribution (anything seed-dependent; mean and spread over several seeds).
- **DM1/T6** A synthetic dataset is a mock of reality, and a clean one tests only the happy path. Build the fixture from failures actually seen, small enough to work by hand: a sentinel, a duplicate key, a sensor unreachable at the peak, a value revised after the fact, both daylight-saving boundaries, a category never seen in training. Commit it with its expected output; it is the cheapest test in the repository.
- **DM1/T7** A code review shows the diff in the code, not in the output, and in a data system the output is the change that matters; "shouldn't change anything" is a hypothesis testable in seconds against the fixture. Commit a golden output, regenerate it on every change, and review the diff: unexpected is a finding, expected is documented in the same commit.
- **DM1/T8** A model's properties: invariance (renaming a lot does not change its forecast), direction (more tickets sold must not predict more free spaces), minimum functionality (cases any working model gets right). Each runs in seconds and catches what an aggregate score hides. For transforms the properties are row counts, key uniqueness, conservation of totals.
- **DM1/T9** An overall score is an average over slices and can be fine while one is broken: the small lots, the concerts, the under-represented; Simpson's paradox is the extreme. Choose slices with the question, before results, so they are not chosen to flatter, and report each with its *n* and interval. A slice is a group and its error is the treatment the group receives: where bias becomes checkable.
- **DM1/T10** When correctness is owned elsewhere, a reference library's algorithm, the original runtime of an exported model, a paper's published number, test against it directly within a tolerance: your estimator against the library on the same input, the export against the training framework on real inputs, your reproduction against the paper with the gap explained.
- **DM1/T11** Clusters, association rules, embeddings, and anomaly scores have no answer key, which makes them the easiest results to believe. Test stability under resampling (clusters that rearrange were drawn, not found), under the arbitrary choices (seed, *k*, distance, scaling: a pattern surviving one setting is a property of the setting), and with a domain expert shown five members of each cluster, not centroids. A rule that stands out among thousands is expected by chance.
- **DM1/T12** The dumb baseline for a search system is not another search but a person or model reading the whole document: run it on a sample before trusting any retrieval, and report what the search missed, by how each page was read. Equal treatment is not recall: the same fixed searches can miss the same thing in every case. Ask whether hybrid search beats `grep` by more than its complexity costs, and hold the test questions away from whoever tunes the search, or the test becomes a training set.
- **DM1/T13** A run is one data point for one question: say before it what result would count against the claim, since a run with nothing at stake is a look that counts and tests nothing. Start small, one lot, one configuration; a small run can clear the next size and cannot stand in for it. Every run gets a ledger line whatever it cost; what is attached scales with the cost of running it again, from commit, data version, seed, environment, and result up to everything you may keep for a holdout look. A limit on keeping data about people comes first: then hashes, counts, the command, and what can no longer be checked.

## 7. Operating

- **DM1/O1** The result, not only the build, depends on the environment: a different BLAS, a GPU instead of a CPU, a minor version with a changed default, and a metric moves in the third digit or the second. Every trained model and reported number carries the resolved package list, the platform, and the accelerator; saving the package manager's list into the run directory costs nothing.
- **DM1/O2** CI's command goes from raw to report on the committed fixture: every stage, the assertions, the property tests, the golden-output diff, in minutes because the fixture is small. It does not touch the holdout or the full data: it tests that the method runs and is right on known cases; whether it is good is a decision, spent deliberately. A repository with no remote still has one script every change passes through, a gate you can skip.
- **DM1/O3** A model's failure is to keep answering, confidently and wrongly, and accuracy needs the true outcome, which arrives tonight, in years, or never. Monitor what you can see now: each feature's distribution against training and the rate of out-of-envelope inputs; the distribution of predictions and the abstention rate; each source's freshness; then realized error and calibration by slice as labels arrive.
- **DM1/O4** "Drift" is three failures: covariate (the inputs' distribution; compare distributions), prior (how common each outcome is; the prediction rate partly shows it), concept (the input-outcome relationship: a new transit line, same tickets, fewer cars; only realized error shows it). The third is the dangerous one, with inputs and predictions looking normal, which is why label latency belongs in the requirements.
- **DM1/O5** When the input is missing, out of envelope, or late, or the model has drifted, something must still answer, simple enough to trust without monitoring: the baseline, a rule the operators already use, or "no forecast" shown honestly. Decide it with the client, write it in the requirements, test the switch; no fallback turns every upstream outage into a confident wrong answer.
- **DM1/O6** Shadow first: the new model receives live inputs and logs predictions while the old one decides; compare on live data, including the slices, then switch undoably and keep the old model loadable. A scheduled retrain is a deploy though no code changed, and gets the fixture, the properties, and the comparison with the current model before it serves; one inside a judge-approved policy keeps the verdict and still gets the checks.
- **DM1/O7** A feature table and a training set are interfaces to every model trained on them: give each a version (a hash, a dated snapshot, a tag) recorded with every model. Changing a feature's definition is a migration: add beside the old, backfill, retrain and compare, switch readers, then remove. Overwriting in place silently changes every model that reads it, including the one in production.
- **DM1/O8** A data system has more copies than its owners count: every cache and intermediate file, every laptop extract, every notebook output cell, every prompt that pasted rows into a hosted model, an agent's transcripts, and old versions in a store where a deleted row stays until purged. Identifiers printed on a scanned form ride into a text cache and an index, so a scrub lasts only where the data is derived, with a check that shows it searched. A model can disclose its training data and anyone writing to the inputs can poison it: training data is outside the trust boundary, and a model trained on personal data is personal data.
- **DM1/O9** No pipeline step is unbiased by default, and a model that passed at training time can fail later as the population moves. Before deploy, the per-group measures the requirements chose, on the holdout, with *n*, intervals, and calibration per group; then search for the group it does worst on, and since that search is a search, confirm on fresh data. After, the same gaps as labels arrive, and who it is used on against who it was trained on. A gap is a finding whose options go to the client; removing the sensitive column rarely fixes it, since other columns stand in.
- **DM1/O10** A sample hides memory (the frame no longer fits), joins (a key unique in the sample is not across seasons), and time (seconds become hours, so nobody re-runs). Run the full pipeline at real size early, once, timed, and keep the time in the repository guide: it is the cost of running again, which sets what each run keeps. The slow stage is rarely the model.
- **DM1/O11** You can roll back a model, not the data it generated or the behavior it taught: forecasts move drivers, lots fill later, and next season's data says the forecast was wrong. Ship it as the one-way door it is: record what the model decided beside what happened, keep a small random slice that does not follow the model, and say in the model card what the model changes.

## 8. Work

- **DM1/W1** CRISP-DM is the six steps renamed: business and data understanding give the question, unit, outcome, and datasheet; preparation and modeling are develop; evaluation is test; monitoring, usually left out, is maintain. It draws the arrow from evaluation back to business understanding, and in data that arrow is the common case: when evaluation says the question was wrong, rewrite the question, not the model.
- **DM1/W2** The expensive decisions all arrive early, when they feel cheap. Model class, hyperparameters, a feature cost a re-run: loop fast. The outcome, unit, and prediction point cost every feature, label, and result: write it, read it to the client, get an objection. The split costs every number: have someone try to break it. The labeling scheme costs the labels and their budget: pilot on fifty rows, measure agreement. The holdout: once, at a decision. Most arguments run hours on the model class and minutes on the outcome.
- **DM1/W3** Horizontal, all the cleaning, then all the features, then the model, puts the question's first contact with the data in the last week. On day one fetch one lot, compute one feature, score the baseline on a proper split, and make the chart the client will look at; show it; then thicken, each step an experiment the last one cleared, so the column that means something else is found while there is time.
- **DM1/W4** Exploration falls down the waterfall as one more plot, one more join, and no claim at the end. Time-box each exploration and cleaning pass and end it on a fence, something proved: a baseline scored on the real split, a datasheet entry, a plot an expert objected to, the pipeline cold from raw with exit zero, a null written down. A status meeting is not a fence; neither is a cell that ran.
- **DM1/W5** The deadline here produces one more peek at the holdout, one more significant subgroup, one more helpful outlier rule, the null unmentioned, and it feels like trying harder; for a summary the pressure is to be concise and the cost is omission. Change the terrain: raw to report in one command and minutes; the plan and bar first, so a late change is a visible departure; the ledger counting, so the forty-first try is visibly the forty-first; nulls reported when found.
- **DM1/W6** The working set adds the question, the analysis plan, and the ledger. The cheapest documentation nobody writes is what did not work: without it the next person re-runs the dead end, and the count of things tried is lost. A dead end is a finding: what it cost, what would have found it sooner, and what it changed, an assertion in the pipeline, a column note in the datasheet, a line in the plan, or why nothing.
- **DM1/W7** All of it, for a claim: the number with its interval, slices, and count of tries; the raw-to-number command run by someone other than the author, agreeing within tolerance; the datasheet and model card updated; the K4s read to the client; a reviewer who read the joins, filters, splits, and fills; the judge's one-line verdict on this version for what is *(judged)*; what the change must not break, by ID and its words. For an extracted claim, a script re-finds each quotation on its page and a second reader reads a sample whole: that checks words and pages, not omissions.

## 9. People

- **DM1/H1** The domain expert is usually the only loop that catches the most expensive errors, the sensor being replaced, the column whose meaning changed, and cannot see them in a metric. Show what they can judge: a plot over time with anomalies marked, ten raw rows including the strangest five, the five worst predictions, five members of each cluster, the features the model leans on in their words. Their surprise is your K2, found cheaply.
- **DM1/H2** Most K4s are statistical sentences the client cannot evaluate as written. Translate each into their world and read it aloud: missing at random is "a sensor that goes quiet is no likelier to be at a busy lot. True?"; stationarity is "next season's crowds behave like the last three. Anything changing?" The "no, because…" is worth more than any model trained before hearing it.
- **DM1/H3** "The effect isn't there" in week two lets the client stop paying or change the question; in week eleven it is a crisis, and that pressure turns an honest null into a tortured positive. Say it in the tone of a win: a null announced apologetically teaches the team that nulls are failures, and the next one is found later or never.
- **DM1/H4** Here the contract between two people is a definition, what counts as an event, which rows are excluded, and two people each cleaning "the" dataset decide privately, with a third version appearing at the merge. One owner and one implementation per shared definition, one producing command per cleaned dataset; everyone else imports it. A recurring meeting about why two dashboards disagree is a missing contract.
- **DM1/H5** The team's shape becomes the conclusions' shape: whoever owns the pipeline owns the definitions, the definitions decide the results, and the group that defines "full" decides how often lots are full. Choose it on purpose: put definitions where the people they affect can read and contest them, and do not let the team being measured own the measure alone.
- **DM1/H6** "AUC 0.83" means nothing to the person choosing which lots to open. Translate into the decision's terms with the uncertainty attached: not "MAE 11.4 minutes" but "for four events in five, lot C fills within fifteen minutes of the forecast; the fifth can be off by forty." Frequencies are understood more reliably than probabilities and honestly name a reference class rather than the one case; say what the model cannot tell them in the same breath.
- **DM1/H7** A model demo's temptation is to pick the examples that work, which shows the client a model that does not exist and loses their objection. Choose the examples beforehand and write them down: some random, some typical, and the worst the model gets wrong. Show failures as clearly as successes and ask which matter to them; that answer is a requirement.
- **DM1/H8** The discomfort here has shapes, each worth more said than kept: "this is too good" is leakage's first sign; "I keep wanting to look at the holdout" is a look about to be spent; "I don't trust the Sunday labels" is a K4 about to become K3; "the effect went away when I changed the window" is a null being negotiated with. The stand-up adds a question per person: what about the current number do you not believe? A disbelief nobody can name yet goes in FINDINGS as a question.

## 10. Agents

- **DM1/A1** An agent can write the pipeline, train a dozen models, and draft the report in an afternoon, and none of that posed the question better, cleared the provenance, made the labels reliable, or enlarged the holdout. Everything scarce has moved to the question, the provenance, the checks, the review, and the ownership of the claim.
- **DM1/A2** Here the agent's wrongness does not raise: it merges on the wrong key, triples the rows, reports an improved metric, and summarizes fluently, with every artifact looking normal; "it ran and the AUC went up" is the shape of leakage. Require what a run cannot fake: row counts before and after each join, a plot, one prediction traced to its rows. A check the agent is told to run is not a check that runs: put the assertions in the pipeline and the knowable-at check in CI, and make the holdout unreachable rather than forbidden.
- **DM1/A3** An agent searches at machine speed, sixty feature sets, forty configurations, and reports the winner, with the other paths in a transcript nobody reads. Hand it the search and the ledger together: every configuration appended by the code, not by its summary, and the agent's count reported with the result.
- **DM1/A4** An agent in a loop with a score will optimize the score, and a readable holdout will eventually be read as one obvious way to check the work, each reaction spending it. Make it mechanical, not an instruction: outside the working directory or behind a permission it lacks, spent by you at a decision; the plainest answer is a person keeping it on paper, which a shell cannot read. The same for any evaluation set's labels and an assignment's answer key.
- **DM1/A5** What agents do best and humans skip most multiplies here: the hand-computed fixture, row-count and uniqueness assertions around every join, property tests, the golden output, the datasheet's first draft. More models do not multiply; more checks do.
- **DM1/A6** Spend review where K3 lives: joins, filters, splits, fills, time conversions, the outcome's definition. Model code is library calls; a wrong `how=` in a merge or a `fillna(0)` where zero means something is one line and changes every number. Ask for the diff in the numbers with the diff in the code and read the data handling line by line; in extraction, review what was read and dropped.
- **DM1/A7** Delegation is not abdication: if you cannot say which rows, which definition, which split, how many tries, you cannot defend the number, update it next quarter, or notice when it goes wrong. An analysis you cannot explain is a liability, whatever its metric.
- **DM1/A8** Pasting rows into a hosted model, attaching a dataset, or letting an agent read a table discloses it to the provider under their terms and retention, and for people's data may be a use it was not collected for. Decide before the first session what the agent may see, usually the schema and a synthetic sample: agents write good code from a fixture and never need more real data than the task does.
- **DM1/A9** A language model that labels, extracts, classifies, embeds, retrieves, or judges is a model. The prompt and model version are the model: an edit or a provider update is a retrain, so re-evaluate and record both. Its output is a distribution: score several samples and report the spread, and see a judge model disagree with a wrong answer before trusting it; for prose, that is two independent reads of a sample of cases with misses counted, since two reads by one model share a blind spot. Its test set may be in its training: evaluate on questions written after the cutoff or held privately.
- **DM1/A10** A synthetic document tests the code and cannot summarize the real one, so when reading is the task the agent must read the rows, and this is written before the first session: who decided, and what the people in the data were told; which service sees it, under what terms; every copy, including the agent's transcripts, tool output, scratch files, and subagents' logs; that text in a document is evidence, never an instruction; when it is all removed, by what procedure, and whether that procedure has been tried.
